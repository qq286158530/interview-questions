## 题目1：Flink 的架构是怎样的？JobManager、TaskManager、Slot 之间是什么关系？

### 答案

**Flink 架构核心组件：**

Flink 采用主从架构，主要由 **JobManager**（主节点）和 **TaskManager**（从节点）组成。

```
┌─────────────────────────────────────────────────────┐
│                     JobManager                        │
│  ┌──────────────┐  ┌────────────┐  ┌─────────────┐ │
│  │  Dispatcher  │  │ JobMaster  │  │  ResourcerManager │
│  └──────────────┘  └────────────┘  └─────────────┘ │
└─────────────────────────────────────────────────────┘
                          │
                    指令调度 & 资源管理
                          │
┌─────────────────────────────────────────────────────┐
│               TaskManager 集群（N个）                 │
│  ┌─────────────────────────────────────────────┐    │
│  │              TaskManager                     │    │
│  │  ┌────────┐  ┌────────┐  ┌────────┐        │    │
│  │  │ Slot1  │  │ Slot2  │  │ Slot3  │        │    │
│  │  └────────┘  └────────┘  └────────┘        │    │
│  └─────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────┘
```

**三大核心组件职责：**

| 组件 | 职责 |
|------|------|
| **JobManager** | 协调整个 Flink 作业的执行：负责任务调度、资源分配（向 RM 申请 Slot）、Checkpoint 协调、故障恢复。一个集群只有一个 Active JobManager |
| **TaskManager** | 真正执行 Task 的 worker 节点，每个 TM 有多个 Slot，提供计算资源。向 JobManager 注册自己的 Slot 信息 |
| **Slot** | TM 的资源抽象单位，每个 Slot 有固定的资源（内存 + CPU），可以运行一个或多个 Task（子任务） |

**Slot 与 Task 的关系：**

- `TaskSlot` 是 TM 上的资源划分，每个 Slot 有独立的内存（`taskmanager.memory.flink.size` 配置）
- **一个 Slot 可以运行多个子任务（SubTask）**，前提是它们属于同一个 Job 的不同算子
- `parallelism`（并行度）决定了每个算子有多少个 SubTask，但 SubTask 最终运行在多少个 Slot 上，由 Slot 数量和调度策略决定
- 如果 Slot 数量少于并行度，SubTask 会轮流共享 Slot

**图示：Slot 执行 SubTask**

```
TaskManager 1
  Slot 1: Source(parallelism=1) → Map(parallelism=2) → Sink(parallelism=1)
  Slot 2: Map(parallelism=2) 的另一个子任务
  Slot 3: 空闲
```

**常见的 Slot 配置问题：**

- Slot 数量不足会导致作业启动失败（"No pool slots available"）
- 建议 Slot 数量 = TM 数量 × TM 每节点 Slot 数 = 总并行度（或者至少是最大并行度的倍数）

📖 来源：[Apache Flink 官方文档 - 架构](https://nightlies.apache.org/flink/flink-docs-release-1.18/zh/docs/concepts/flink-architecture/)

## 题目2：Flink 的 Watermark 机制是什么？它是如何解决乱序和迟到数据的？

### 答案

**为什么需要 Watermark？**

在事件时间（Event Time）处理模式下，由于网络延迟、系统故障等原因，数据到达的顺序可能和事件发生的顺序不一致（乱序）。Watermark 是 Flink 用来**判断何时认为某窗口的所有数据已经到齐**的核心机制。

**Watermark 的定义：**

Watermark 本质上是一个时间戳（Timestamp），表示"**所有时间戳 ≤ watermark 的数据都已经到达了**"。

```
Watermark(t) = "我确信不会再有时间戳 < t 的数据了"
```

- 当 Watermark 超过窗口结束时间，窗口就会被**触发计算**
- 如果有数据的时间戳 < watermark 但还未被处理，Flink 会将其**丢弃或发送到侧输出流**

**两种 Watermark 策略：**

**1. 固定延迟策略（Fixed Watermark）**
```java
WatermarkStrategy
    .forMonotonousTimestamps()  // 单调递增（最简单）
    .withTimestampAssigner(...)
```
适用场景：事件大致有序，只有少量乱序。

**2. 乱序策略（Allowed Lateness）**
```java
WatermarkStrategy
    .forBoundedOutOfOrderness(Duration.ofSeconds(10))  // 最大乱序等待时间
    .withTimestampAssigner(...)
```
这里的 `Duration.ofSeconds(10)` 表示：允许最大 10 秒的乱序。

**Watermark 传播机制：**

Watermark 会在算子之间传播，一个算子的 watermark  = min(所有输入流的 watermark)：

```
Source (产生 Watermark)
   ↓
Map (传递 watermark，取输入流的最小值)
   ↓
Window (当 watermark >= 窗口_end_time，触发窗口计算)
```

**乱序处理流程：**

```
事件时间 → 0s → 5s → 8s → 3s → 10s → 6s ...
                        ↑
                    乱序到达(3s在8s之后)

Watermark = 当前最大事件时间 - 最大乱序等待时间(5s)

当 watermark >= 窗口结束时间 → 触发窗口计算
```

**迟到数据处理（Allowed Lateness）：**

```java
TumblingEventTimeWindows.of(Time.seconds(10))
    .allowedLateness(Time.seconds(5))  // 窗口关闭后，5秒内的迟到数据还能触发重新计算
    .sideOutputLateData(lateOutputTag) // 更晚的数据发送到侧输出流
```

**三种处理策略对比：**

| 策略 | 行为 | 使用场景 |
|------|------|---------|
| 丢弃（默认） | 扔掉 | 不关心迟到数据 |
| allowedLateness | 在额外窗口期重新触发窗口 | 需要最终一致性的统计 |
| sideOutputLateData | 将迟到数据侧输出 | 需要追踪/补偿迟到数据 |

**Watermark 的痛点：**

- Watermark 推进太慢 → 窗口迟迟不触发
- Watermark 推进太快 → 有效数据被丢弃
- 多流合并时，整体 watermark 取决于最慢的那条流

📖 来源：[Apache Flink 官方文档 - Watermark](https://nightlies.apache.org/flink/flink-docs-release-1.18/zh/docs/concepts/time/#event-time-and-watermarks)

## 题目3：Flink Checkpoint 和 Savepoint 的区别是什么？Flink 是如何实现 exactly-once 语义保证的？

### 答案

**Checkpoint vs Savepoint 对比：**

| 维度 | Checkpoint | Savepoint |
|------|-----------|-----------|
| **触发方式** | Flink 自动周期性触发（JobManager 调度） | 手动触发（用户通过 CLI 或 API） |
| **用途** | 故障恢复，作业重启后自动从最近 checkpoint 恢复 | 计划性维护（作业升级、集群迁移、A/B测试） |
| **存储位置** | 由 Flink 管理（可配置） | 用户指定目录 |
| **保留策略** | 新 checkpoint 完成后自动删除旧 checkpoint | 一直保留，需手动删除 |
| **状态格式** | 作业的轻量快照 | 完整的作业状态快照 |

**两者共同点：** 都基于 Flink 的**分布式快照算法（Chandy-Lamport 变体）** 实现。

---

**Flink  Exactly-Once 语义实现原理：**

Flink 的 exactly-once 靠 **Checkpoint + 状态后端 + 2PC 两阶段提交** 配合实现：

**Step 1：Checkpoint 快照（Chandy-Lamport 分布式快照）**

Flink 在数据流中插入**屏障（Barrier）**，作为检查点的边界标记：

```
数据流: Data1 | Data2 | [Barrier] | Data3 | Data4 | [Barrier] | ...
              ↑                                         ↑
         Checkpoint 1 的 barrier                   Checkpoint 2 的 barrier
```

**流程：**
1. JobManager 定期向所有 Source 算子发送 `CheckpointCoordinator` 消息，触发 checkpoint
2. Source 算子收到消息后，保存自己的状态（偏移量），然后向下游广播 Barrier
3. 中间算子收到所有输入的 Barrier 后（对齐等待），保存状态，然后向下游转发 Barrier
4. Sink 算子收到 Barrier 并完成状态保存后，向 CheckpointCoordinator 确认
5. 全部确认后，Checkpoint 完成

**Step 2：两阶段提交（2PC）实现端到端 exactly-once**

对于有外部输出的算子（如写入 Kafka/Pulsar），Flink 使用 **两阶段提交协议**：

```
阶段1: preCommit
  - Sink 算子预提交（写缓存、准备提交），阻塞等待所有输入的 Barrier
  - 完成后进入"预提交"状态

阶段2: commit
  - Checkpoint 状态存储完成后，JobManager 通知所有算子正式提交
  - Sink 算子真正将数据写入外部系统
  - 如果失败，Flink 会从最近 checkpoint 恢复并重试
```

**Exactly-Once 的关键前提：**

| 组件 | 要求 |
|------|------|
| Source | 支持rewind（可以从某个offset重新消费）|
| 状态后端 | 如 RocksDB、Flink Managed State |
| Sink | 必须支持 2PC（如 Kafka 0.11+ Producer 的事务） |

**Kafka Sink 的 Exactly-Once 实现：**

```java
KafkaSink<String> sink = KafkaSink.<String>builder()
    .setBootstrapServers("localhost:9092")
    .setRecordSerializer(KafkaRecordSerializationSchema.builder()
        .setTopic("output-topic")
        .setValueSerializationSchema(new SimpleStringSchema())
        .build())
    .setDeliveryGuarantee(DeliveryGuarantee.EXACTLY_ONCE)
    .setTransactionalIdPrefix("my-flink-job")
    .build();
```

Kafka 使用幂等性 Producer + 事务来保证 Sink 的 exactly-once。

📖 来源：[Apache Flink 官方文档 - Checkpointing](https://nightlies.apache.org/flink/flink-docs-release-1.18/zh/docs/ops/state/checkpoints/)

## 题目4：Flink 窗口函数有哪几种？滚动窗口、滑动窗口、会话窗口的区别是什么？

### 答案

**窗口的三种分类维度：**

1. **按时间对齐 vs 按数据量对齐**：Time Window vs Count Window
2. **按大小是否重叠**：滚动窗口（Tumbling）vs 滑动窗口（Sliding）
3. **按是否有固定边界**：滚动、滑动、全局、会话窗口

**一、滚动窗口（Tumbling Window）**

窗口大小固定，窗口之间**不重叠**，首尾相接。

```java
// 每5分钟一个窗口，互不重叠
TumblingEventTimeWindows.of(Time.minutes(5))

// 每10条数据一个窗口
SlidingProcessingTimeWindows.of(Time.seconds(10), Time.seconds(10)) 
// 注意：滚动窗口本质是滑动窗口的特殊情况（滑动步长 = 窗口大小）
```

```
时间轴: |----窗口1(0-5min)----|----窗口2(5-10min)----|----窗口3(10-15min)----|→
数据    ↑事件A            ↑事件B ↑事件C              ↑事件D
```

**特点：** 无重叠、数据不会重复计算、适合固定周期统计（如每天UV、每5分钟订单数）

---

**二、滑动窗口（Sliding Window）**

窗口大小固定，但可以按固定步长滑动，**窗口之间可以有重叠**。

```java
// 窗口大小10分钟，滑动步长5分钟（每5分钟输出一次过去10分钟的统计）
SlidingEventTimeWindows.of(Time.minutes(10), Time.minutes(5))
```

```
时间轴: |----窗口1(0-10min)----|
              |----窗口2(5-15min)----|
                    |----窗口3(10-20min)----|→

数据:      A      B    C        D       E
```

**特点：** 适合"平滑统计"场景（移动平均），窗口重叠越大，计算成本越高

---

**三、会话窗口（Session Window）**

没有固定大小，根据**会话间隔**（Gap）动态创建窗口。两个事件之间如果间隔超过 Gap，则开启新窗口。

```java
// 会话间隔为10秒的会话窗口
SessionWindows.withGap(Time.seconds(10))
```

```
数据:  A  B    C        D      E(间隔超过10s，新会话开启)  F    G
      |----会话1----|       |----会话2----|
```

**动态会话窗口（动态 Gap）：**

```java
// 根据每条数据的"gap"属性动态确定会话间隔
SessionWindows.withDynamicGap(new SessionWindowTimeGapExtractor<Tuple2<String, Long>>() {
    @Override
    public long extract(Tuple2<String, Long> element) {
        return element.f1; // 从数据中提取间隔
    }
})
```

**特点：** 适合用户行为分析（用户会话），无法预知窗口边界

---

**三种窗口对比：**

| 特性 | 滚动窗口 | 滑动窗口 | 会话窗口 |
|------|---------|---------|---------|
| 窗口大小 | 固定 | 固定 | 动态 |
| 是否有重叠 | 否 | 是 | 否 |
| 触发时机 | 窗口结束时 | 每次滑动步长到达 | Gap 空闲超时 |
| 适用场景 | 固定周期统计 | 移动平滑统计 | 用户会话行为 |
| 内存占用 | 低 | 中（取决于滑动步长） | 中 |

---

**Count Window（计数窗口）：**

除了时间窗口，Flink 还支持按元素数量触发窗口：

```java
// 每100条数据计算一次
.countWindow(100)

// 每100条数据计算一次，但每50条滑动一次（类似滑动窗口的概念）
.countWindow(100, 50)
```

**注意：** 生产环境尽量使用时间窗口而非计数窗口，因为数据延迟会导致计数窗口迟迟不触发。

📖 来源：[Apache Flink 官方文档 - Windows](https://nightlies.apache.org/flink/flink-docs-release-1.18/zh/docs/dev/datastream/operators/windows/)

## 题目5：Flink 背压（Back Pressure）是如何产生的？如何诊断和解决？

### 答案

**背压产生的原因：**

背压（Back Pressure）是指下游算子的**处理速度跟不上游数据的发送速度**，导致上游算子被迫降低数据发送速率的现象。

```
Source → Map → Window(Slow) → Sink
          ↑                       ↑
      正常速度              处理速度慢 → 背压向上传导
```

**典型背压场景：**

| 场景 | 原因 |
|------|------|
| 窗口计算瓶颈 | 窗口内数据量过大（如大状态窗口）|
| 外部 I/O 阻塞 | Sink 写入数据库/Kafka 速度慢 |
| 状态访问过频 | 使用 RocksDB 状态后端，频繁序列化/反序列化 |
| 数据倾斜 | KeyBy 后热点 Key 导致某些 SubTask 负载过高 |
| 机器资源不足 | CPU/内存瓶颈，TM 资源耗尽 |

**Flink 的背压传播机制（TCP 拥塞控制）：**

Flink 使用 **TCP 流控** 来处理背压：
- 算子之间通过 Netty 网络栈通信
- 当下游 SubTask 的接收缓冲区满了，上游自动降速
- 背压沿着数据流方向向上传导

```
Socket → TaskManager1(Socket缓冲区满) ← TaskManager2的Socket发送
            ↓
        Netty 检测到背压
            ↓
        降低 Source 的数据发送速率
```

**如何诊断背压？**

**方法1：Flink Web UI 查看（最直接）**

打开 Flink Dashboard → 选择 Job → 点击某个 Task → 查看 **Back Pressure** 列：
- `OK`（绿色）：无背压，处理正常
- `LOW`（浅蓝）：轻微背压
- `HIGH`（红色）：严重背压，需关注

**方法2：背压采样（Rest API）**

```bash
# 查看某个 Job 的背压状态
curl http://<jobmanager>:8081/jobs/<job-id>/vertices/<vertex-id>/backpressure
```

**方法3：Flink Metrics 监控**

监控以下关键 Metrics：

| Metric | 含义 |
|--------|------|
| `currentInputQueueLength` | 输入队列长度，越高说明挤压越严重 |
| `numRecordsInPerSecond` | 每秒输入记录数 |
| `numRecordsOutPerSecond` | 每秒输出记录数 |
| `heavyUsage` | RocksDB 状态后端的相关指标 |

**如何解决背压？**

| 解决方案 | 适用场景 |
|---------|---------|
| 增加并行度 | 整体负载过高，处理能力不足 |
| 调整 TM/Slot 资源配置 | 资源瓶颈（内存/CPU不足） |
| 优化状态后端 | RocksDB 序列化慢 → 换用 HeapStateBackend 或优化序列化器 |
| KeyBy 数据倾斜 → 加盐 | 热点 Key 导致个别 SubTask 负载过高 |
| 异步 I/O | Sink 写入外部系统慢 → 改用 Async I/O |
| 减少 Checkpoint 频率 | Checkpoint 阻塞数据处理 |
| 增加 Sink 并行度 | Sink 是瓶颈时有效 |
| 使用反压策略 | Flink 1.9+ 自动反压（Adaptive Batch Scheduler）|

**反压的正常范围：**

- 轻微背压（LOW）是正常的，尤其在数据流高峰时
- 持续 HIGH 背压需要立即排查
- 背压也可能和 GC 有关（Flink GC 停顿导致处理变慢）→ 检查 TM GC 日志

**生产环境建议：**

1. 开启 **Prometheus + Grafana** 监控背压 Metrics
2. 配置 `taskmanager.network.memory.fraction` 适当调大网络缓冲区
3. 定期检查 Flink 日志中的 `OutOfMemoryError` 或 `CheckpointFailure`

📖 来源：[Apache Flink 官方文档 - 反压](https://nightlies.apache.org/flink/flink-docs-release-1.18/zh/docs/ops/debugging/job_debugging/#back-pressure)
